# Prism — Performance engineering

Performance is a requirement, not a polish pass. This document defines the budgets, the methodology
used to verify them, and the profiling recipes contributors must run before changing hot paths.

## 1. Budgets

| Scenario                          | Budget                          | Failure consequence      |
| :-------------------------------- | :------------------------------ | :----------------------- |
| Idle RSS (library loaded, paused) | **< 50 MB**                     | Release blocked          |
| Idle CPU                          | **< 0.5 %** of one core         | Release blocked          |
| Cold start → first painted frame  | **< 300 ms**                    | Release blocked          |
| Library scroll, 500k rows         | **120 FPS**, no blank artefacts | Release blocked          |
| Interaction latency (INP)         | **< 16 ms**                     | Investigate before merge |
| Layout shift (CLS)                | **0**                           | Release blocked          |
| Metadata scan, 100k FLAC          | **< 10 s** warm NVMe            | Investigate              |
| Gapless transition error          | **0 samples**                   | Release blocked          |
| Audio callback deadline misses    | **0** during normal playback    | Release blocked          |

Reference machine for gate measurements: 8-core x86-64, 32 GB RAM, NVMe SSD, Windows 11 24H2 and
Ubuntu 24.04, 1440p 144 Hz display. Results from other hardware are recorded but do not gate a
release unless they regress relative to the previous tagged build.

## 2. Backend methodology

### Startup

- `tracing` timestamps: process start, subscriber ready, database opened, migrations applied, window
  shown, first IPC round-trip.
- Windows: ETW/WPA "Application Startup" trace. Linux: `hyperfine` for process time plus internal
  markers for the split between Rust and WebView paint.

### Idle

- 10-minute soak after a full library load; RSS via `ps_mem` (Linux) and Private Bytes (Windows);
  CPU as a 60-second average after the UI settles.

### Audio

- A loopback capture compares output samples against the decoded source for bit-perfect paths.
- Gapless: synthetic album with 1-sample silence boundaries; assert no dropped/duplicated frames
  across 1 000 transitions.
- Latency: cpal timestamp deltas vs. monotonic clock; xrun counters from ALSA/PipeWire logs.

### Scanning

- `cargo flamegraph --profile profiling -- scan <root>` on a synthetic 100k-file tree (FLAC headers
  generated by the fixture tool). The gate is wall-clock and CPU time, not instruction count.
- SQLite: `PRAGMA optimize` after large batches; `EXPLAIN QUERY PLAN` snapshots are committed for the
  top-20 queries in `docs/queries/` once FASE 3 lands.

### Memory and UB

- `cargo +nightly miri test` for DSP and CUE parser modules (pure code, no OS calls).
- `valgrind --tool=memcheck` on Linux integration tests that exercise CUE parsing and playback buffer
  lifecycle; `heaptrack` for allocation growth across 10 000 track changes.
- `loom` models for the SPSC ring buffer once FASE 2 lands (feature-gated, CI nightly job).

### Leak checks

- Change track 10 000 times and assert RSS returns to ±2 MB of baseline.
- Open/close the audio device 500 times; file descriptors and WASAPI/ALSA handles must return to
  baseline.

## 3. Frontend methodology

- **React Profiler** in development with the "Highlight updates" overlay; any commit over 4 ms in the
  library view is investigated.
- **Chrome/WebKit performance traces** while scrolling with `pointer` wheel events at maximum speed
  for 60 seconds. Success criteria: no frame > 8.3 ms p95, no long tasks > 50 ms, zero blank rows.
- **Virtualisation audit**: `@tanstack/react-virtual` measurement cache stays warm; row components are
  memoised; formatters are module-level singletons; no `Intl` construction inside render.
- **State isolation**: assert with React DevTools that a playhead tick re-renders only `ProgressBar`
  (and its leaf), never `TrackList`. The FFT meter subscribes through `useSyncExternalStore` to a
  non-React ring buffer.
- **CLS**: Lighthouse/DevTools layout-instability trace must report 0; skeletons match final geometry.
- **GPU**: ambient background uses compositor-only properties. Canvas/WebGL visualisers run in a
  worker with `OffscreenCanvas`; the main thread only posts frames.

## 4. How to profile

```bash
# Rust
cargo install flamegraph
cargo flamegraph --profile profiling --bin prism
# Linux only, detailed allocations
heaptrack target/profiling/prism

# Frontend
pnpm dev
# Chrome DevTools → Performance → CPU 4x throttle → record scroll
```

Tracy integration (`tracing-tracy`) is enabled behind the `profiling` profile once the audio engine
lands; frame and callback zones are annotated at the thread boundary.

## 5. Regression gates

CI runs functional tests only. Performance gates run before a release on the reference machine and
are recorded in `docs/benchmarks/` with the tag, commit and hardware. A release checklist item
requires the four hard budgets above to pass; results are attached to the GitHub Release notes.
