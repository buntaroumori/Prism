# Releasing Prism

A release is a tag. Everything else — the quality gate, the native bundles, the notes, the checksums
— is a consequence of that tag, because a release that depends on a human remembering a step is a
release that will eventually be wrong.

This document describes the contract: what a version means, which files carry it, what the pipeline
does, what is validated _before_ the tag exists, and what to do when something goes wrong.

---

## 1. Versioning

Prism follows [Semantic Versioning](https://semver.org/spec/v2.0.0.html) with the usual 0.x
exception: while the minor version is `0`, a **minor** bump may contain breaking changes to the
plugin API or the database schema, and a **patch** bump never does.

| Change                                                                 | Bump                                                    |
| :--------------------------------------------------------------------- | :------------------------------------------------------ |
| Breaking change to the plugin host API, the IPC contract or the schema | minor (`0.1` → `0.2`)                                   |
| New feature, no contract break                                         | minor                                                   |
| Bug fix, performance work, documentation                               | patch                                                   |
| Pre-release (`0.2.0-rc.1`)                                             | suffix — GitHub marks it as a pre-release automatically |

Schema migrations are forward-only and additive while the minor version holds: a `0.1.x` release must
open a database written by any other `0.1.y`. A migration that rewrites user data is a minor bump.

## 2. Version carriers

Four files state the version, and they must agree or the pipeline stops in its first job:

| File                                 | Field                                   |
| :----------------------------------- | :-------------------------------------- |
| `package.json`                       | `version`                               |
| `Cargo.toml` (`[workspace.package]`) | `version`                               |
| `src-tauri/Cargo.toml`               | inherits via `version.workspace = true` |
| `src-tauri/tauri.conf.json`          | `version`                               |

```bash
node scripts/check-version.mjs          # compares the three carriers
node scripts/check-version.mjs v0.2.0   # …and the tag you are about to push
```

## 3. Changelog discipline

`CHANGELOG.md` is [Keep a Changelog](https://keepachangelog.com/en/1.1.0/) shaped: an `[Unreleased]`
section at the top, one `## [x.y.z]` section per release, and the categories `Added`, `Changed`,
`Deprecated`, `Removed`, `Fixed`, `Performance` and `Security`.

Every user-visible change lands in `[Unreleased]` **in the pull request that makes it**. On release
day, `[Unreleased]` is renamed to the version, the date is added, and a fresh empty `[Unreleased]` is
created above it.

The release notes published on GitHub are the `## [x.y.z]` section verbatim, with the commit list
appended in a collapsed block. They are generated by `scripts/generate-changelog.mjs`, which falls
back to commit-derived notes and says so if the section is missing — a release never ships an empty
description.

## 4. Cutting a release

```bash
# 1. Prepare, on a branch, through a pull request.
#    - bump the three version carriers
#    - move [Unreleased] under ## [x.y.z] — YYYY-MM-DD
#    - regenerate the licence inventory if the dependency graph moved
pnpm licenses
node scripts/check-version.mjs v0.2.0
python3 scripts/validate_release.py v0.2.0

# 2. Merge, then tag the merge commit.
git checkout main && git pull
git tag -a v0.2.0 -m "Release v0.2.0"
git push origin v0.2.0

# 3. Watch .github/workflows/release.yml run, then verify the release page.
```

The tag must be annotated (`-a`); the pipeline reads it and refuses a mismatch between the tag and
the manifests, which is the failure mode that produces a release named after one version and built
from another.

## 5. What the pipeline does

`release.yml`, triggered by **any `v*` tag**:

| Job       | Runs on                          | What it proves                                                                                                                                                                                                                                         |
| :-------- | :------------------------------- | :----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `quality` | `ubuntu-24.04`                   | versions agree with the tag; dependency licences pass and `docs/LICENSES.md` is current; the release workflow itself validates; frontend typechecks, lints, formats and builds; the SQLite schema harness passes; Rust formats, lints clean and tests. |
| `bundle`  | `windows-latest`, `ubuntu-24.04` | the app compiles natively on both platforms and produces installable artefacts.                                                                                                                                                                        |
| `publish` | `ubuntu-24.04`                   | checksums, licence inventory, notes and the GitHub Release.                                                                                                                                                                                            |

`bundle` and `publish` are gated on `quality`; `concurrency` is serialised per tag and never
cancels, so two releases cannot race.

### Artefacts

| Platform | File                               | Built from                                                 |
| :------- | :--------------------------------- | :--------------------------------------------------------- |
| Windows  | `Prism_<version>_x64.msi`          | `bundle/msi` (WiX)                                         |
| Windows  | `Prism_<version>_x64_setup.exe`    | `bundle/nsis`                                              |
| Windows  | `Prism_<version>_x64_portable.exe` | the release binary, copied                                 |
| Linux    | `Prism_<version>_amd64.AppImage`   | `bundle/appimage`                                          |
| Linux    | `Prism_<version>_amd64.deb`        | `bundle/deb`                                               |
| All      | `THIRD-PARTY-LICENSES.md`          | `docs/LICENSES.md`, copied byte for byte                   |
| All      | `SHA256SUMS.txt`                   | `sha256sum` over the directory, regenerated after the copy |

Bundling targets come from `bundle.targets` in `src-tauri/tauri.conf.json` (`nsis`, `msi`,
`appimage`, `deb`). Release builds use **default features only**: `profiling` and `asio` are not
enabled, so no debugger, no profiler and no SDK-dependent code enters an artefact.

## 6. What is validated before the tag exists

`python3 scripts/validate_release.py` is a static validator, not a dry run: it cannot create a
Windows bundle on a Linux box, but it can prove that the workflow would find what it expects.
Thirty checks, in four groups:

| Group          | Checks                                                                                                                                                                              |
| :------------- | :---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Versions       | three carriers agree; the tag matches; `rust-toolchain.toml` pins the toolchain used by CI                                                                                          |
| Workflow shape | YAML parses; `push.tags: v*`; `contents: write`; the three jobs exist and chain `quality → bundle → publish`; both platforms are in the matrix; concurrency never cancels           |
| Hygiene        | every `uses:` is pinned to a version tag or a commit (with one documented exception); every `scripts/…` a step calls exists; no `secrets.*` inside `if:`; no `continue-on-error`    |
| Artefacts      | every `bundle.targets` entry has a staging step; every staged file is matched by a published glob; checksums and the licence inventory are published; notes come from the changelog |
| Licensing      | `LICENSE` is MIT with a copyright line; `package.json`, `Cargo.toml` and the bundle metadata say MIT; the audit passes and the document is current                                  |

The validator earns its place by failing on real mistakes. Deleting the `deb` staging line, for
example, is caught immediately:

```
[FAIL] stages deb                                     copies from bundle/deb
```

CI runs it on every pull request (`licenses` job, with `--skip-licence` because the audit step
already ran) and again in the release `quality` job, so a broken pipeline is found on a Tuesday
afternoon rather than during the release.

## 7. Verifying a published release

```bash
gh release download v0.1.0 --dir /tmp/prism-0.1.0
cd /tmp/prism-0.1.0 && sha256sum -c SHA256SUMS.txt
```

Then install the artefact for your platform and check the two numbers a user notices: startup time
and that silence between tracks is silence. `docs/PERFORMANCE.md` has the reference budgets.

## 8. If something is wrong

| Symptom                                      | Action                                                                                                                                                        |
| :------------------------------------------- | :------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `quality` fails before bundling              | fix `main`, delete the tag (`git push --delete origin v0.2.0`), re-tag. Nothing was published.                                                                |
| A bundle fails on one platform               | same: no release exists yet, so the tag is free to move.                                                                                                      |
| The release is published with a bad artefact | edit the release to a pre-release, publish a fixed patch version, and leave the broken one in place — deleting a published tag breaks everyone who pinned it. |
| The notes are wrong                          | edit the release body; the next release regenerates from `CHANGELOG.md`.                                                                                      |

## 9. Signing

Windows Authenticode and minisign for the updater are **not** wired yet: the certificates do not
exist, and a pipeline that pretends to sign is worse than one that does not. When they land, the
release job gains a `TAURI_SIGNING_PRIVATE_KEY` secret, `bundle.createUpdaterArtifacts` flips to
`true`, and the workflow fails closed if the key is missing — never publishes unsigned silently.
